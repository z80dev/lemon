# Work screens

`WorkScreen` consumes the canonical SDK endpoints and shared app/query/action UI. It handles `skills`, `routines`, `connect.apps`, `connector.setup`, `integrations.channels`, `integrations.email` and `integrations.x`. These screens do not create a scheduler, mailbox, OAuth service or provider credential store in the browser.

## Reviewed workflows

- **Skills:** owner library search, publisher/source/trust provenance, Markdown editing and preview, text-file import into the unsaved editor, explicitly selected owned-host installation, enable/disable, owned-Bot assignment and confirmed host-backed deletion. Skills have no Team scope or other-human maintainer grants. A saved skill is not an executed task.
- **Routines:** save active or paused schedules with a five-field cron and IANA timezone, authenticated webhooks, advertised channel events or exact external event definitions. External filters are typed from the provider's self-contained schema and must satisfy every selected event. An unrestricted message listener requires unchecked-by-default human `noisyListenerConsent`, reset whenever its exact Bot/binding/channel/phrase scope changes; copied/model configuration cannot grant it. Broad listener resumption uses the reviewed active-save editor, while pausing remains available without renewed consent. Test starts actual work, not a dry run. Pausing stops future triggers; cancellation addresses a selected active run. History preserves error, status, timestamps, known/unknown cost and a private results link. A `route.entryId` identifies an exact routine-run independently of history pagination. Chat editing drafts into the owner's existing private Bot conversation; it does not send the prompt. Destructive deletion uses the server preview/token/name/revision. Webhook header/key/URL copying is explicit; rotation invalidates the old key and revocation stops ingress.
- **Apps:** registered provider discovery is separate from actual account connection. Configure a real HTTPS streamable MCP server on the labelled assigned machine; select existing secret names rather than entering credentials in headers. Existing header bindings are never guessed from the names-only projection: replacement is a deliberate complete mapping. Auth status is polled through the canonical auth resource, with reopen/reconnect, denial/expiry/block/failure states. Tools replace the full current enabled-tool list. Removal requires server scope preview. Consent resolves only for the exact account owner, with concrete server/account/Bot/private-request context and optional remembered expiry; revocation only prevents future use. Connector-ID-only card routes resolve through authorized paginated Bot/account inventories.
- **Channels:** select actual registered provider IDs, inspect configuration prerequisites and advertised capabilities, perform the provider OAuth/app-install flow and poll real pending/admin/connected/denied/failed state. Existing configured adapter accounts can be bound to a reviewed target. Binding edits and removal use the current revision; uninstall failures remain errors rather than successful cleanup. Linking issues an own-account code, presents it externally through the actual provider DM instructions, polls for the signed observed sender, then explicitly confirms that verified identity with the separate verification proof. Arbitrary product user/external identity mapping is not an editor option. Channel-ID links fetch and render the exact authorized binding.
- **Email:** provider/domain discovery → actual availability → exact owned-Bot permissions proposal → explicit approval resolution → provider claim. Approval alone is never displayed as a provisioned account. Actual mailbox queries/read views retain authentication/scan status, withheld bodies and skipped attachment metadata. Only a measured `indexingDelayed: true` renders a delay warning; false is a retained no-delay observation, absent/null is unknown, and observation time/age never implies current health. Provider reads are not a simulated inbox or new-mail notification service. Outgoing drafts select and verify an actual active owned source mailbox matching exact From, review recipients/body/attachments, upload actual selected files, save/discard separately and require explicit exact-content Send. Sending/unknown are not editable or silently retried. All mail replies/routines retain this Send requirement.
- **X:** inspect the actual registered public handle, OAuth scopes, media/region capabilities and operator prerequisites, choose an owned main Bot and explicitly authorize. Initial and reconnect authorization receipts use the same real status polling; account lookup respects pagination. Mention dispatch enablement and main-Bot changes use the current revision. Disconnect is explicit. Public acceptance is not private completion and protected-account MCP scopes remain separate.

## Failure and authority rules

Reads surface errors, never empty/idle fallbacks. Mutations send a fresh nonce per explicit intent and the current revision where required; no mutation or approval is queued offline or automatically replayed. Ambiguous writes retain input, fence the form and offer an explicit current-state read instead of resend. Sending email and unknown provider results remain visibly unconfirmed. Owner checks constrain the UI; the backend remains authoritative. Time-bound controls update locally so an expired gate cannot remain visually actionable while awaiting realtime reconciliation.

Credentials are never placed into transcript, provider discovery, URLs, generic JSON forms or local persistence. The browser holds only one-time explicitly displayed linking/webhook material and selected file/editor state. Real host/provider availability and permissions remain prerequisites, not fake setup success.

Hosts, connector accounts and channel bindings belong to the signed-in owner. Connector setup never offers shared-account authorization or another human's credentials; provider discovery, actual OAuth state, exact owner consent and host prerequisites remain separate. Machine settings edit only names and labels, never crosshuman access. Files, names-only secrets, host operations and interactive PTY terminals retain their existing privileged-host boundaries. Direct process execution is not an interactive terminal.

No builds, tests, lint, format or provider probes are performed in this slice. The integrating lead should check TypeScript/SDK conformance and exercise the flows against configured providers, including offline read errors, stale revisions, gate expiry, partial upload/unknown outcomes, pagination/deep links, provider-admin denial and ACL read-only behavior.
